# ggml-npu 设计说明

## 1. 当前主线

当前 `ggml-npu` 主线已经统一为：

1. 不修改 `npuruntime`
2. 所有分块、地址分配、pack/repack、执行编排都放在 `ggml/src/ggml-npu`
3. 激活采用“离线提取参数的静态非对称量化”
4. 权重在 `plan_create` 阶段完成 AOT pack
5. `sum(q_w)` 补偿项在 `plan_create` 阶段预计算
6. `transpose` 继续走 CPU 路径，不下发 NPU

静态参数表来自离线校准文件，执行期只读取，不在线重新估计。

## 2. 当前量化语义

当前主线的 activation 量化语义是：

- 对当前 matmul 的整个 activation tensor 计算一次 `absmax`
- 得到单个 `scale = absmax / 127`
- 按这个单一 `scale` 把整个 activation tensor 量化成 `int8`
- `zero_point = 0`

因此当前路线是：

- activation：per-tensor dynamic symmetric int8
- weight：对称 int8
- bias：仅在 `head/single` 阶段按 `bias / (s_a * s_w)` 映射到 int32
- ACC：跨 K 子块直接累加

这条路线的目标是先对齐 NPU 需要的“plain contiguous int8 + ACC 累加”执行语义，而不是复用 ggml 的 `Q8_0` block-scale 执行语义。

## 3. 为什么不用 ggml baseline 的 block 动态量化

当前 `Q8_0` GGUF 权重是 ggml 的块量化格式：

- 每 32 个值一个 scale
- 沿 K 维前进时，不同 block 的 scale 可能不同

而当前 NPU 路线希望的是：

- activation / weight 在 DRAM 上是普通连续 `int8`
- K 子块在 ACC 中直接累加

如果继续沿用 ggml baseline 那种 block-scale 语义，那么跨 K 直接累加会遇到 scale 不一致问题。  
因此当前先把 `ggml-npu` 主线收敛到：

- activation：整个 tensor 一个 scale
- weight：每输出列一个 scale

这样就能让：

- `head/body/tail`
- bias 注入
- ACC 跨 K 累加

都保持比较直接的整数语义。

## 4. 和 npux-mlir 的对应关系

当前设计继续对齐你给的 `npux-mlir` 路径：

1. 第一次分块：`Conversion/NpuTiling/Gemm.cpp`
2. 插入 DMA：`Conversion/NpuTiling/NpuInsertDma.cpp`
3. 第二次分块：`Conversion/NpuTiling/NpuOpSplitting.cpp`
4. 内存规划：`Conversion/NpuToLLVM/NpuMemPlan.cpp`

其中：

- 第一次分块负责按 SRAM 容量求 `Tm/Tn/Tk`
- 第二次分块负责按 SA `32x32` 做微分块
- `ggml-npu` 当前自己维护 offset 规划
- runtime 只接收已经算好的 offset 和尺寸

## 5. SPM / ACC 语义

当前统一约定：

- `SPM` 对应 `npux-mlir` 里的 `encode2`
- `ACC` 对应 `npux-mlir` 里的 `memory3 / encode3`

并且 runtime 侧地址统一按“偏移值”理解：

- `SPM` 是一整块独立内存
- `ACC` 是另一整块独立内存
- GEMM / DMA 看到的地址参数都只是各自空间内的 offset

例如：

- A 放在 `SPM offset 0`
- A 如果占 `64B`
- 那么 B 可以放在 `SPM offset 64`

当前 `ggml-npu` 已经按这个语义静态计算：

- activation 的 `SPM offset`
- weight 的 `SPM offset`
- accumulator 的 `ACC offset`

## 6. 分块策略

当前仍然保留两级分块：

1. 第一级：按 SRAM/ACC 容量计算 `Tm/Tn/Tk`
2. 第二级：按 SA 做 `32x32` 微分块，并沿 K 再切成 `stage2_k_block`

默认语义继续对齐 `matmul_integer`：

- 输出不占 `SPM`
- 中间结果保留在 `ACC`
- 最终结果从 `ACC` 回写 DRAM

所以执行顺序是：

1. 先按 `Tm/Tn/Tk` 形成宏块
2. 宏块内部再按 `32x32` 形成 `M/N` 微块
3. 如果 `Tk > stage2_k_block`，再沿 K 切子块
4. 每个 K 子块执行一次 GEMM，并在 ACC 中累加

## 7. head / body / tail 语义

当前计划层已经显式生成：

- `single`
- `head`
- `body`
- `tail`

语义如下：

- `head`
  第一次 K 循环
- `body`
  中间 K 循环
- `tail`
  最后一次 K 循环
- `single`
  整个 matmul 只有一次 K 循环

同时当前还保留两个编译期标志：

- `needs_bias`
  仅 `head/single` 为真
- `writes_output`
  仅 `tail/single` 为真

这正对应你前面强调的语义：

- 只有第一次 K 循环加 bias
- 只有最后一次 K 循环写最终输出

## 8. AOT 与运行时边界

当前已经按 AOT 完成的内容：

- `M/N/K` 静态形状
- 第一次分块 `Tm/Tn/Tk`
- 第二次分块 `32x32 + stage2_k_block`
- `SPM/ACC` offset 分配
- static weight pack
- `exec_tile` 和 `head/body/tail` 计划

当前仍然放在运行时的内容：

- 根据实际 activation 数值计算整 tensor `scale`
- 把 activation 按该 `scale` 量化成连续 `int8`
- 把该次输入对应的量化结果搬运到 `SPM`

所以当前边界是：

- 几何、地址、切块、weight pack 是 AOT
- activation 量化值 materialization 是运行时

这和“weight 编译时确定，所以 weight 的 pack 应该在编译时做完”的要求是一致的。

## 9. bias 处理

当前 bias 仍走轻量融合：

- `ADD(MUL_MAT(...), bias)`
- `ADD(bias, MUL_MAT(...))`

当前主线里：

- bias 不再带非对称补偿项
- 仅在 `head/single` 阶段按 `bias / (s_a * s_w)` 转成 int32 注入

## 10. transpose 策略

当前仍然不把 transpose 下发到 NPU。

采用的策略是：

- transpose 使用 CPU 算子
- NPU 路径只消费已经整理好的 matmul 输入
- 如果需要布局重排，则在 `pack/repack` 阶段完成

## 11. 当前限制

当前版本还有限制：

- 只支持 2D contiguous matmul
- 只支持 `F32` 输出
- `SPM/ACC` 仍使用占位容量参数，真实值后续再填
- 还是单 node 工作集，不是 `NpuMemPlan.cpp` 那种模块级 allocator/reuse
- runtime C API 的完整验证链路还没打通
- 当前 whole-tensor dynamic quant 是为了先对齐 NPU 语义，不等于最终精度/性能最优方案

## 12. 当前结论

现在这版 `ggml-npu` 更准确的描述是：

- 识别 matmul / bias-fused matmul
- 在 `ggml-npu` 内完成两级分块、offset 规划和 weight AOT pack
- 运行时对整个 activation tensor 做一次动态对称量化
- 以 plain contiguous int8 的方式喂给 NPU
- 通过 `head/body/tail` 控制 bias 注入、ACC 累加和最终输出
